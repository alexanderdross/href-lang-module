# Web Performance

Performance is a hard constraint. The rule: **the mapping system must add ~zero
cost to serving a page.** All the expensive work (matching, embeddings, LLM,
validation) happens off the request path; page render only reads pre-computed,
cached data.

## 1. Golden rule - no cross-backend calls at request time

A page render **never** calls the hub or a sibling backend. Each backend keeps a
local, denormalized **alternates store** (a table keyed by URL) that the
Distributor refreshes out-of-band. If the hub is down, pages still render with
the last known-good alternates. Latency added to a request ≈ one indexed local
read, already inside Drupal's render cache.

## 2. Caching & precise invalidation

- **Render cache + cache tags.** Attach each page's hreflang output with a cache
  tag per **translation group** (e.g. `hrefl_group:UUID`). When a mapping
  changes, invalidate only that tag → only the affected pages rebuild. No
  site-wide clears.
- **Cache contexts.** Alternates are per-URL and language-agnostic to the
  visitor, so they cache cleanly at page, dynamic-page-cache, and CDN/edge
  layers.
- **Pre-computation.** The Distributor resolves the full per-URL alternate set
  (absolute URLs, codes, x-default) *before* it reaches the client, so the
  client never computes reciprocity at render time.

## 3. hreflang carrier: sitemap-first at scale

For a large family, injecting the full alternate set into every page's `<head>`
adds bytes to every response. Best practice at scale is the **XML sitemap as the
primary hreflang carrier**, with `<head>` tags optional for robustness.

- Sitemaps are generated by the module's **own multilingual sitemap generator**
  in `hrefl_client` (simple_sitemap is single-language here and not used for
  this), **off-peak on cron**, **incrementally**, and **chunked** to respect the
  50,000-URL / 50 MB limits, then **gzipped**.
- Head-tag emission can be enabled per section (e.g. top pages) so the smallest
  useful set ships in HTML while the sitemap carries the full graph.
- Both carriers read the identical local store, so they never disagree.

## 4. The country/language selector must stay cheap

- Rendered from **static page data** (the page's own alternates attached via
  `drupalSettings`/inlined JSON) - **no per-request API call**, no client-side
  round trip to build the menu.
- **Crawlable real `<a href>` links** (progressive enhancement), so it is
  edge-cacheable and bot-followable; JS only enhances interaction.
- **No layout shift (CLS):** reserve space; avoid late-injected DOM. Keep the
  component's JS/CSS tiny and defer non-critical parts.
- **No auto-redirect** on load (see §6) - the page the user requested is the
  page that renders.

## 5. Keep matching off the request path

- Embeddings and LLM adjudication run in **queue workers**, batched, rate-limited,
  scheduled off-peak.
- **Embeddings are cached** per content version; a re-edit re-embeds only the
  changed page. Vector search uses an ANN index, not brute force.
- Hub **ingest/serve endpoints are batch/cron**, never in a visitor's request;
  they can be rate-limited and throttled without user impact.
- Validation crawls (200/canonical checks) are async and de-duplicated.

## 6. No IP/geo auto-redirects (performance + SEO + UX)

Automatic locale redirects add a redirect hop (latency, wasted crawl budget),
can trap or mislead users and bots, and hurt Core Web Vitals. **Excluded by
design.** Users switch market/language only via the selector; hreflang tells
search engines which localized URL to rank for a given audience. See
`docs/SEO.md` for the SEO rationale.

## 7. Hub scalability

- Ingest/serve behind the Global backend; heavy work (matching, embedding,
  target validation) in queues off the request path.
- Incremental where it counts: matching and embedding are cursor-based and only
  touch never-/least-recently-processed members (fair pass); publish walks the
  corpus with a nid cursor. **Note:** the client *pull* currently re-fetches the
  whole resolved set and swaps the local store atomically (guarded so an empty
  pull never wipes it); a `since` cursor on pull is a future optimization, not a
  correctness requirement. The hub *serve* builds a market's set in one indexed
  pass - fine off the render path, and the scaling point to watch at very large
  markets.
- Back-pressure: queues smooth publish spikes; retries with exponential backoff.

## 8. Performance budget (targets to verify)

- Added server time per page from hreflang: **< 2 ms** (local cached read).
- Added `<head>` weight where head tags are on: **minimal** (sitemap carries the
  bulk).
- Selector: **0 blocking requests**, **0 CLS**, **< a few KB** JS/CSS.
- Sitemap generation: built from the local store and served with a 1-hour edge
  cache header (not rebuilt per request on a cache hit); reads never call the hub
  or siblings.
- Mapping freshness (event → live alternate): **minutes**, not the next daily
  cron.
